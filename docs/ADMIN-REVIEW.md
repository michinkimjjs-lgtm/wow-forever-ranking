# 관리자 검토

> 단계: Phase 3A
>
> 구현:
> - 화면 `app/admin/submissions/page.tsx`, `app/admin/login/page.tsx`, `app/admin/actions.ts`
> - 로그인 `lib/admin/session.ts`
> - 처리 `lib/submissions/admin-review.ts`

## 1. 접근과 인증

- 관리자 화면은 `SUBMISSIONS_ADMIN_TOKEN`(32자 이상)과 `SUBMISSION_SECRET`(32자 이상)이 모두 설정된 배포에서만 열립니다. 설정이 없으면 404입니다.
- 로그인: `/admin/login`에서 관리자 토큰을 입력합니다.
  - 비교는 상수 시간으로 합니다.
  - 로그인 시도는 일시 식별값 기준 15분에 10회로 제한합니다.
- 로그인 쿠키 `fr_admin_session`:
  - 값은 `만료 시각.서명`입니다. 서명은 HMAC(SUBMISSION_SECRET, 만료 시각 + 관리자 토큰 해시)입니다.
  - 토큰 원문은 들어 있지 않습니다.
  - 속성: `HttpOnly`, `SameSite=Strict`, `Path=/admin`. 운영 환경에서는 `Secure`도 붙습니다.
  - 유지 시간은 8시간입니다(`config/submissions.ts`).
  - 관리자 토큰을 바꾸면 기존 로그인은 모두 무효가 됩니다.
- 검토 버튼은 Next.js 서버 액션입니다.
  - Next.js가 Origin과 Host를 비교해 다른 사이트의 요청을 거부합니다.
  - 액션마다 로그인을 다시 확인합니다.
- 관리자 화면은 `noindex`입니다.

## 2. 목록 (`/admin/submissions`)

| 열 | 내용 |
|---|---|
| 제출 ID | UUID 앞 8자 (마우스를 올리면 전체) |
| 캐릭터 | 이름 + 상세 보기 |
| 제출 경로 · 데이터 출처 (Phase 4A) | 공개 제출 화면에서 올린 파일: "웹 업로드" · "커뮤니티 제출". 관리자 API: "관리자 API" |
| 제출 시각 / 데이터 시각 | KST |
| 레벨 | |
| 장비 coverage | 미리보기 기준 (슬롯 매핑 프로필) |
| 검증 상태 | 항상 "커뮤니티 제출" |
| 중복 | 같은 export가 다시 제출된 횟수 |
| 충돌 | CONFLICT이거나 비교에서 충돌이 있으면 "있음" |
| 처리 상태 | 검토 대기 / 반영됨 / 반영 안 함 / 충돌 검토. 매핑 대기 표시 |

- 상태별 필터와 건수를 표시하고, 50건씩 보여 줍니다.
- 상세 보기:
  - 제출 내용 (미리보기 항목)
  - 이전 제출과 달라진 항목
  - 확인된 문제
  - 동의 기록 (버전, 시각)
  - 검토 시각, 검토 메모
  - 제출 경로, 데이터 출처, 검토 상태 (Phase 4A)
  - Collector 버전, Export 형식 버전 (Phase 4A부터 저장. 이전 기록은 "-")
- mock 배포에서는 "테스트 데이터 환경에는 제출 기록이 없습니다."를 표시합니다.

## 3. 검토 상태

| 코드 | 화면 | 뜻 | 랭킹 반영 |
|---|---|---|---|
| `PENDING` | 검토 대기 | 공개 제출 기본값 | 안 됨 |
| `CONFLICT` | 충돌 검토 | 이전 제출과 충돌 | 안 됨 |
| `ACCEPTED` | 반영됨 | 관리자가 승인 (또는 관리자 API로 바로 반영) | **됨** |
| `REJECTED` | 반영 안 함 | 관리자가 거부 | 안 됨 |

검토 상태는 검증 상태와 다릅니다.

- 반영됨이어도 검증 상태는 `COMMUNITY_SUBMITTED`(커뮤니티 제출)입니다.
- `character_submissions`의 CHECK 제약이 `verification_status = 'COMMUNITY_SUBMITTED'`를 강제합니다.

## 4. 처리

### 랭킹에 반영 (승인)

1. 보관한 export를 다시 스키마 검증합니다.
2. **현재 매핑 설정**으로 다시 정규화합니다.
   - 관측 시각이 너무 오래되었는지는 제출 시각 기준으로 판단합니다. 검토가 늦어도 거부하지 않기 위해서입니다.
   - 매핑이 아직 없으면 반영하지 않습니다. 결과는 "게임 값 매핑이 아직 없어 반영할 수 없습니다."이고 `MAPPING_PENDING`이 유지됩니다.
3. 이미 반영된 제출과만 다시 비교합니다.
   - 충돌이 있으면 "충돌 내용을 확인했고 반영합니다"를 선택해야 반영됩니다.
   - 선택하지 않으면 `CONFLICT`로 둡니다.
4. 수집 파이프라인(`ingestObservation`)에 반영합니다.
   - 원본 보관, 식별, 현재 상태, 장비, 스냅샷, milestone을 처리합니다.
   - 레벨 감소처럼 파이프라인이 식별 충돌로 판단하면 현재 상태를 바꾸지 않고 `CONFLICT`가 됩니다.
5. 결과를 기록합니다: 검토 시각, 메모(최대 500자), 연결된 캐릭터 ID와 수집 기록 ID.

### 반영 안 함 (거부)

- 검토 상태를 `REJECTED`로 바꾸고 시각과 메모를 남깁니다.
- 랭킹은 바뀌지 않습니다. 제출 기록은 지우지 않습니다.

이미 처리한 제출(`ACCEPTED`, `REJECTED`)은 다시 처리할 수 없습니다.

## 5. 검토 기준 (권장)

| 확인 | 기준 |
|---|---|
| 레벨 | 최대 레벨 설정을 넘지 않는지. 이전 반영값보다 낮지 않은지 |
| 관측 시각 | 레벨 상승 기록과 시각 순서가 맞는지 |
| 장비 | 아이템 레벨이 레벨에 비해 비정상적으로 높지 않은지. coverage가 낮으면 장비 랭킹에서 자동 제외됨 |
| 중복 | 같은 export가 여러 번 제출되었는지 (`중복` 열) |
| 충돌 | 직업 변경, 레벨 감소, GUID 불일치 |
| 매핑 대기 | 원본 값으로 `config/export-mapping.ts`를 확정할 수 있는지 (실제 첫 제출의 핵심 용도) |

검토 기준의 숫자(예: 비정상 아이템 레벨)는 실제 데이터가 쌓이면 정합니다.
