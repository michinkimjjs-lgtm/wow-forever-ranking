## 0. 결론 요약

1. **지금 가장 현실적인 방법은 "사용자 본인 캐릭터 Collector 제출"입니다.**
   - 공식 Forever API는 공개되지 않았습니다.
   - 제3자 서비스 데이터는 이용 조건상 쓸 수 없거나 확인되지 않았습니다.
2. 랭킹은 3단계로 키웁니다.
   - 커뮤니티 레벨 랭킹
   - Forever Rank 커뮤니티 랭킹
   - 공식 데이터 기반 랭킹
3. 공식 API가 열리기 전에는 "전체 서버 1위"라고 표시하지 않습니다.
4. Blizzard API가 열리면 Provider 설정만 추가해 연결합니다. 현재 설계는 버리지 않습니다.

## 1. 전략 비교

| 항목 | A. Blizzard 공식 API | B. 사용자 제출 Collector | C. 독립 커뮤니티 Collector Network |
|---|---|---|---|
| 지금 가능한가 | **불가** (Forever API 미공개) | **가능** (Collector·검증·제출 API 구현됨. 공개 업로드 화면만 남음) | 설계 가능. Uploader가 필요 |
| 구현 난이도 | 낮음~중간. Provider 구조 완료, endpoint·정규화만 추가 | 낮음. 남은 것: 공개 업로드 화면, 동의, rate limit | 중간. Uploader 앱 배포·서명·업데이트, 제출자 익명 키, 중복·충돌 처리 |
| 데이터 범위 | 전체 캐릭터 (API가 허용하는 범위) | 제출한 사람의 캐릭터만 | B보다 넓음. 여전히 참여자 캐릭터만 |
| 정확도 | 높음 (공식) | 중간. 클라이언트 값은 정확하지만 조작 가능성 있음 | 중간~높음. 반복 제출·독립 동의로 교차 확인 |
| 최신성 | 수집 주기에 따름 (높음) | 낮음. 사용자가 제출할 때만 | 중간. Uploader가 로그아웃 후 자동 제출 |
| 확장성 | 높음 (호출 한도 안에서) | 낮음. 사람 손에 의존 | 중간. 참여자 수에 비례 |
| 개인정보 위험 | 낮음 (공개 데이터, 약관 준수) | 낮음. 본인 데이터, 동의 기반 | 중간. 설치 앱이 파일을 읽으므로 범위 제한·투명성 필요 |
| 운영 비용 | API 호출·작업 큐 | 낮음 | 중간. 앱 배포, 서명, 지원 |
| 전체 랭킹 가능 | **가능** (전수에 가까움) | **불가**. "확인한 캐릭터 중 순위"만 | **불가**. 커버리지가 커져도 모집단을 모름 |

정리:

- A가 열리면 A가 최우선 공급원입니다.
- 그 전에는 B로 시작하고, 참여가 늘면 C로 넓힙니다.
- B와 C는 같은 Character Export 형식과 같은 서버 검증을 씁니다. 그래서 C는 B 위에 Uploader만 추가하는 것입니다.

## 2. 핵심 질문에 대한 답

### Q1. 사용자가 게임에 접속하지 않고도 개발을 계속할 수 있는가?

**예.** 다음은 게임 없이 개발하고 테스트할 수 있습니다.

- 서버 전체: 제출 검증·정규화·식별·랭킹·커버리지·단계 판단·화면
- 공개 업로드 화면, 동의 화면, rate limit, 삭제 요청 처리, 관리자 검토 화면
- Uploader(Companion)의 파일 읽기·전송 로직: 샘플 export 파일로 테스트
- Collector 애드온의 로직: Lua 하네스(`addon/tests`)로 테스트

게임이 필요한 일은 **실제 값 확인**뿐입니다. 이것은 개발자가 아니라 게임에 접속할 수 있는 다른 사용자가 한 번 실행해 주면 됩니다(Q3).

- 직업·종족 코드와 한국어 명칭
- 슬롯 번호
- `Enum` 값
- 이름과 성을 잇는 구분자
- SavedVariables 저장 동작

### Q2. 우리 사이트가 직접 캐릭터 데이터를 수집하는 방법은?

| 방법 | 지금 | 비고 |
|---|---|---|
| 공식 API로 서버가 직접 수집 | 불가 | 공개되면 유일한 "직접 수집" 방법 |
| 사용자가 Collector export를 제출 | 가능 | 본인 캐릭터만. 우리가 "받는" 방식 |
| 제3자 사이트 scraping / 제3자 API | **금지** | DATA-SOURCE-POLICY §2, §4 |
| 게임 안에서 다른 플레이어 수집(`/who`, inspect) | **금지** | 동의 없는 타인 데이터 |

공식 API가 없는 동안 우리 서버가 스스로 캐릭터 데이터를 "가져오는" 방법은 없습니다. 사용자가 보내 준 본인 데이터만 받습니다.

### Q3. 게임에 접속할 수 있는 다른 사용자가 Collector를 한 번만 실행해도 제출할 수 있는가?

**예. 설계상 한 번이면 됩니다.**

1. Collector 설치
2. 게임 접속
3. `/frc export`
4. 로그아웃 또는 `/reload` (SavedVariables 파일이 디스크에 기록됨)
5. `WTF/Account/<계정>/SavedVariables/ForeverRankCollector.lua` 파일을 사이트에 업로드

주의할 점:

- SavedVariables를 **다시 읽지 못하는** 버그가 보고되었습니다(FOREVER-API-CAPABILITY §2-7). 파일 **쓰기**는 정상으로 보고되었으므로 한 번 실행 후 제출하는 흐름에는 영향이 없습니다. 실제 동작은 게임 내 실행 검증이 필요합니다.
- 폴더 경로에 계정 이름이 들어 있습니다. 업로드 화면과 Uploader는 **파일 내용만** 보내고 경로는 보내지 않습니다.
- 지금 서버 제출 API는 관리자 토큰 전용입니다(기능 플래그 기본 꺼짐). 공개 업로드 화면과 동의 화면을 만들어야 다른 사용자가 직접 제출할 수 있습니다. 다음 단계에 포함합니다.

### Q4. 몇 명이 Collector를 사용해야 "커뮤니티 랭킹"이라고 부를 수 있는가?

**정확한 숫자는 지금 정하지 않습니다.** 근거 없이 정한 숫자는 신뢰를 주지 못하기 때문입니다.

- 1단계 "커뮤니티 레벨 랭킹"은 **제출이 한 건이라도 있으면** 씁니다.
  - 이 이름 자체가 "커뮤니티가 제출한 캐릭터 기준"이라는 범위를 밝히기 때문입니다.
  - 화면에는 "Forever Rank가 확인한 캐릭터 N명"을 함께 표시합니다.
- 2단계 "Forever Rank 커뮤니티 랭킹"은 숫자가 아니라 **관찰 지표**로 정합니다([`DATA-COVERAGE-MODEL.md`](./DATA-COVERAGE-MODEL.md) §3-3).
  - 독립 제출자 수
  - 직업·진영 다양성
  - 상위권 안정성
  - 충돌 비율
  - 실제 데이터로 분포를 본 뒤 기준값을 정합니다(`config/community-ranking.ts`, 현재 모두 미정).
- 통계적으로 적절한 표현:
  - "N명 중 1위", "커뮤니티 제출 기준"
  - **비율(%)과 "전체 서버"는 모집단을 모르므로 쓰지 않습니다.**

### Q5. Blizzard API가 열리면 현재 설계를 버리지 않고 바로 연결할 수 있는가?

**예.**

- `BlizzardProvider`는 설정 → capability → endpoint → 인증 → 정규화 구조로 이미 만들어져 있습니다. 공개되면 다음만 추가합니다.
  - capability를 AVAILABLE로
  - endpoint 등록
  - 응답 정규화 코드
- 공식 데이터도 같은 정규화 관측 형식으로 같은 수집 파이프라인을 통과합니다. DB·랭킹 엔진·화면은 그대로입니다.
- 같은 캐릭터의 연결:
  - 공식 ID는 `character_external_refs`에 넣습니다.
  - 기존 제출 캐릭터와는 자연 키(region + gameMode + 전체 이름)로 이어집니다.
- 우선순위 규칙(`VERIFIED → … → MOCK`)은 이미 구현되어 있습니다(`lib/domain/source-priority.ts`).
- 화면은 활성 캐릭터가 모두 공식 데이터가 되면 자동으로 "공식 데이터 기반 랭킹"으로 바뀝니다(`classifyRankingStage`).

## 3. 랭킹 이름 단계

| 단계 | 조건 | 랭킹 이름 | 순위 표현 |
|---|---|---|---|
| 0. 테스트 | mock 배포 | 레벨 랭킹 + "테스트 데이터" | N위 (테스트 데이터) |
| 1. 커뮤니티 | 커뮤니티 제출 데이터 | **커뮤니티 레벨 랭킹** / 커뮤니티 장비 랭킹 / 커뮤니티 최고 아이템 | Forever Rank 확인 캐릭터 중 N위 |
| 2. 브랜드 커뮤니티 | 관찰 지표 기준 충족 (기준값 미정) | **Forever Rank 커뮤니티 랭킹** | Forever Rank 확인 캐릭터 중 N위 |
| 3. 공식 | 활성 캐릭터 전부 공식 공급원 | **공식 데이터 기반 랭킹** | 공식 데이터 기준 N위 |
| 3+. 전체 서버 | §5 조건 모두 충족 | 공식 데이터 기반 랭킹 | **전체 서버 N위** |

공식 데이터와 커뮤니티 제출이 섞여 있으면 1·2단계 이름을 유지합니다. 공식 데이터만으로 순위를 만들 수 있게 되면 그 데이터만으로 3단계 랭킹을 따로 계산하는 방식을 공식 API 단계에서 검토합니다.

## 4. 신뢰도 용어

| 용어 | 종류 | 뜻 |
|---|---|---|
| 공식 | 출처 | Blizzard 공식 API에서 온 데이터 |
| 검증됨 | 검증 상태 | 공식 공급원 등으로 확인 (`VERIFIED`) |
| 로그 검증 | 검증 상태 | 전투 로그 등으로 확인 (`LOG_VERIFIED`, 향후) |
| 커뮤니티 제출 | 출처 / 검증 상태 | 사용자·애드온 제출 (`COMMUNITY_SUBMITTED`). Phase 2D에서 "사용자 제출"에서 이름을 바꿈 |
| 미검증 | 검증 상태 | 출처를 확인할 수 없음 (`UNVERIFIED`) |
| 테스트 데이터 | 출처 / 검증 상태 | mock (`MOCK`) |

## 5. "전체 서버 1위" 표시 조건

[`DATA-COVERAGE-MODEL.md`](./DATA-COVERAGE-MODEL.md) §5를 따릅니다. 요약:

| 관점 | 조건 |
|---|---|
| 데이터 커버리지 | 공식 근거로 아는 모집단 대비 확인 비율 ≥ 기준 |
| 데이터 최신성 | 7일 안에 확인한 캐릭터만 집계 |
| 검증된 출처 비율 | 활성 캐릭터가 모두 공식 공급원, 검증 비율 ≥ 기준 |
| 중복 캐릭터 검증 | 식별 충돌 비율 ≤ 기준 |
| 동일 캐릭터 여러 제출 비교 | 충돌 제출(CONFLICT)이 랭킹 상위에 없음 (공식 단계에서 함께 적용) |
| 조작 가능성 | 사용자 제출만으로는 어떤 경우에도 불가 |

충분한 근거가 없으면 "전체 서버 1위"라고 표시하지 않습니다. 현재 설정으로는 항상 표시하지 않습니다.

## 6. 독립 Collector Network 구조

```text
Player
  ↓ 본인 캐릭터로 게임 접속
ForeverRankCollector (애드온, 인터넷 통신 없음)
  ↓ /frc export → SavedVariables 파일
Export (Character Export v1 JSON)
  ↓ 사용자 업로드 (웹 화면) 또는 Companion/Uploader (별도 앱, 사용자 동의 후)
Forever Rank Server — POST /api/v1/submissions/character
  ↓ 크기 제한 · rate limit · 형식 검증 (Phase 2B-1 구현)
Validation
  ↓ 정규화 · 금지 필드 제거 · 서버가 dataEnvironment 부여 · COMMUNITY_SUBMITTED
Character DB
  ↓ 식별(§7) · 원본 보관 · 스냅샷 · milestone · 장비 계산
Ranking
    서버 계산 · 커버리지 · 단계 이름 · 출처 표시
```

Companion/Uploader 원칙 (P1 이후, 설계만):

- 애드온은 인터넷 통신을 하지 않습니다. 전송은 Uploader가 합니다.
- Uploader는 `ForeverRankCollector.lua` **한 파일만** 읽습니다. 다른 애드온 파일, 계정 이름, 폴더 경로는 보내지 않습니다.
- 처음 실행할 때 보낼 항목과 공개 범위를 보여 주고 동의를 받습니다. 자동 전송은 사용자가 켜야 동작합니다.
- 설치마다 임의로 만든 익명 제출자 키를 붙입니다. 계정 정보와 연결하지 않습니다.
- 게임 클라이언트 파일을 수정하거나 게임 메모리를 읽지 않습니다. 게임 플레이를 자동화하지 않습니다.
- 배포 파일에 checksum과 서명을 붙입니다.

## 7. 캐릭터 식별

Realm은 추가하지 않습니다. Forever는 realm이 없고, 전체 이름(이름 + 성)이 region 안에서 고유합니다(FOREVER-API-CAPABILITY §2-3).

### 우선순위

| 순서 | 키 | 출처 | 구현 |
|---|---|---|---|
| 1 | Stable external identifier | 공식 API 캐릭터 ID (공개되면) | `character_external_refs` (`data_source = blizzard`) |
| 2 | GUID | Collector `UnitGUID("player")` | `character_external_refs` (`data_source = user_submission`) |
| 3 | region + gameMode + 전체 이름 | 정규화(NFC + 소문자) | 자연 키 `(data_environment, region, game_mode, name_normalized)` |
| 4 | 제출 이력 | 레벨·직업 흐름 비교 | `compareSubmissions` |

- 판단 코드: `lib/domain/submission-consistency.ts` (`identityKeyOf`, `groupByCharacter`, `compareSubmissions`)
- 저장 시 식별: 기존 `lib/ingestion/ingest.ts`

### 정책

| 상황 | 처리 |
|---|---|
| 같은 GUID, 이름 대소문자·공백만 다름 | 같은 캐릭터 |
| 같은 GUID, 이름이 바뀜 | 이름 변경으로 보고 같은 캐릭터 유지 (`NAME_CHANGED`, info) |
| 같은 이름, 서로 다른 GUID | 이름 재사용 또는 조작 가능성. 충돌(`STRONG_ID_MISMATCH`). GUID 없는 제출을 어느 쪽에도 붙이지 않음 |
| 같은 이름, 다른 게임 모드 | 다른 캐릭터 |
| 시간이 지나 레벨이 낮아짐 | 충돌(`LEVEL_DECREASE`). 현재 상태에 반영하지 않음 (기존 식별 충돌 규칙) |
| 거의 같은 시각(5분 안)에 레벨이 다름 | 충돌(`SAME_TIME_DIFFERENT_LEVEL`). 조작 가능성 |
| 직업이 바뀜 | 충돌(`CLASS_CHANGED`) |
| 종족·진영이 바뀜 | 경고. Forever에서 종족·진영 변경 서비스가 있는지는 확인 필요 |
| 서로 다른 제출자가 최신 상태에 동의 | `CORROBORATED`. 검증 상태는 그대로 `COMMUNITY_SUBMITTED` |
| 같은 제출자의 반복 제출 | 독립 동의로 세지 않음 |

충돌 데이터는 삭제하지 않고 원본을 보관합니다. 관리자 검토 화면은 P1에서 만듭니다.

## 8. 현재 사이트 UI 반영 (Phase 2D)

- 랭킹 화면 제목이 단계에 따라 바뀝니다.
  - beta / live: "커뮤니티 레벨 랭킹"
  - mock: 기존 이름에 "테스트 데이터" 배지
- 랭킹 화면 상단 "데이터 안내" 패널:
  - 데이터 기준 (최근 확인 날짜, KST)
  - 데이터 범위 ("Forever Rank가 확인한 캐릭터 N명 (최근 7일)")
  - 데이터 출처 (공식 / 커뮤니티 제출 / 테스트 데이터)
  - 검증 상태
  - 순위 의미 ("순위는 Forever Rank가 확인한 캐릭터 안에서의 순위입니다.")
- "전체 서버" 문구는 허용 판단을 통과할 때만 씁니다. 현재는 어디에도 표시되지 않습니다.

## 9. 외부 서비스와 충돌을 피하는 방법

- 외부 서비스의 데이터를 가져오지 않습니다. 그래서 데이터 소유권·약관 충돌이 생기지 않습니다.
- Raider.IO Forever API는 사용하지 않습니다(경쟁 서비스 구축 금지).
- 외부 사이트를 scraping하지 않습니다. robots.txt나 공개 페이지라는 이유로 권한을 가정하지 않습니다.
- `/who` 기반 census처럼 다른 플레이어를 수집하는 방식은 쓰지 않습니다. 본인 데이터만 받습니다.
- 다른 서비스의 화면 구성·코드를 복사하지 않습니다. 공개 API 문서는 사실 정보만 참조합니다.
- 다른 서비스와 수치가 다를 수 있습니다. 화면에 우리 데이터 범위("Forever Rank가 확인한 캐릭터")를 밝혀 혼동을 막습니다.
