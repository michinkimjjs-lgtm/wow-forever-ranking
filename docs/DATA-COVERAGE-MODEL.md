# 데이터 커버리지 모델

> 단계: Phase 2D
>
> 구현:
> - 커버리지 계산: `lib/ranking/coverage.ts`
> - 단계 판단과 "전체 서버" 표시 판단: `lib/ranking/community.ts`
> - 정책 값: `config/community-ranking.ts` (DRAFT, 기준값 모두 미정)

## 1. 왜 필요한가

랭킹 1위가 의미 있으려면 "누구를 보고 1위인지"를 밝혀야 합니다.

- 공식 API가 없는 지금은 Forever Rank가 **확인한 캐릭터**만 압니다. 전체 캐릭터 수(모집단)는 모릅니다.
- 그래서 지금 할 수 있는 말은 "Forever Rank가 확인한 N명 중 1위"까지입니다.
- "전체 서버 1위"는 모집단을 사실상 전부 보고 있다는 근거가 있을 때만 쓸 수 있습니다.

## 2. 측정 항목 (`DataCoverage`)

모든 값은 하나의 `dataEnvironment` + `gameMode` 안에서 계산합니다. mock과 실제 데이터를 섞지 않습니다.

| 항목 | 정의 | 현재 계산 |
|---|---|---|
| `observedCharacters` | 한 번이라도 확인한 캐릭터 | ✓ |
| `activeCharacters` | 최근 7일(`staleAfterDays`) 안에 확인한 캐릭터 | ✓ |
| `staleCharacters` | 확인한 지 7일이 넘은 캐릭터 (랭킹 제외, 삭제 안 함) | ✓ |
| `rankableCharacters` | 활성 캐릭터 중 랭킹에 포함되는 검증 상태. 필터 없는 레벨 랭킹 대상 수와 같음 | ✓ |
| `byVerification`, `bySource` | 활성 캐릭터의 검증 상태별·공급원별 수 | ✓ |
| `origins` | 활성 캐릭터에 나타난 출처 구분 (공식 / 커뮤니티 제출 / 테스트 데이터) | ✓ |
| `verifiedRatio` | (검증됨 + 로그 검증) ÷ 활성 | ✓ |
| `officialRatio` | 공식 공급원 ÷ 활성 | ✓ |
| `identityConflicts` | 같은 기간 식별 충돌로 기록된 수집 건수 | ✓ |
| `latestSeenAt` | 가장 최근 확인 시각 (화면의 "데이터 기준") | ✓ |
| `populationEstimate` | 모집단 추정치 | **null** (근거 없음) |
| `independentSubmitters` | 서로 다른 제출자 수 | **null** (제출자 단위 집계 없음, P1) |

## 3. 통계적으로 맞는 표현

### 3-1. 지금 쓸 수 있는 표현

| 상황 | 표현 | 쓰지 않는 표현 |
|---|---|---|
| 모집단을 모름 | "Forever Rank가 확인한 캐릭터 N명" | "전체의 N%" |
| 순위 | "Forever Rank 확인 캐릭터 중 1위" | "전체 서버 1위", "서버 최고" |
| 자발적 제출 | "커뮤니티 제출 기준" | "대표 표본", "추정 순위" |

### 3-2. 이유

1. **비율을 계산할 분모가 없습니다.** 모집단 수를 공식적으로 알 수 없으므로 "%"를 쓰면 숫자를 만들어 내는 것이 됩니다.
2. **자발적 제출은 무작위 표본이 아닙니다.** 상위권 플레이어가 더 많이 제출할 수도, 덜 제출할 수도 있습니다(선택 편향). 그래서 신뢰 구간 같은 표본 통계를 적용할 수 없습니다.
3. **1위는 표본으로 추정할 수 없습니다.**
   - 무작위 표본이라고 가정해도 실제 1위가 표본에 들어 있을 확률은 대략 커버리지 비율과 같습니다.
   - 예를 들어 50%를 보면 1위를 놓칠 확률도 약 50%입니다.
   - "전체 서버 1위"에는 표본이 아니라 **전수에 가까운 데이터**가 필요합니다. 현실적으로는 공식 API뿐입니다.
4. **제3자 census 수치는 분모로 쓰지 않습니다.** 이용 조건을 확인하지 못했고(DATA-SOURCE-POLICY §0), `/who` 기반 집계 방식도 우리 정책과 다릅니다.

### 3-3. "커뮤니티 랭킹"이라고 부를 만한 근거 (Q4)

정확한 인원수를 지금 정하지 않습니다. 실제 제출 데이터로 아래 지표를 관찰한 뒤 정합니다.

| 지표 | 의미 | 측정 방법 |
|---|---|---|
| 독립 제출자 수 | 한 사람이 여러 캐릭터를 올린 것과 구분 | Uploader 익명 키 (P1) |
| 활성 캐릭터 수 | 7일 안에 확인한 캐릭터 | `activeCharacters` |
| 다양성 | 직업·진영·게임 모드별로 빈 칸이 없는지 | `byClass`, `byFaction` 추가 (P1) |
| 상위권 안정성 | 새 제출이 들어와도 상위 K명이 크게 바뀌지 않는지 | 주 단위로 상위 K 겹침 비율 기록 (P1) |
| 충돌 비율 | 식별 충돌·제출 충돌 비율 | `identityConflicts / activeCharacters` |
| 독립 동의 | 같은 캐릭터 상태에 서로 다른 제출자가 동의한 비율 | `compareSubmissions().independentAgreements` |

판단 원칙: **"상위권 안정성"이 일정 기간 유지되고 충돌 비율이 낮으면** "Forever Rank 커뮤니티 랭킹"으로 부릅니다. 그 전까지는 "커뮤니티 레벨 랭킹"입니다.

## 4. 단계 판단 (`classifyRankingStage`)

| 단계 | 조건 | 화면 이름 (레벨) |
|---|---|---|
| `TEST_DATA` | mock 배포 | 레벨 랭킹 + "테스트 데이터" 표시 |
| `COMMUNITY` | 기본 | 커뮤니티 레벨 랭킹 |
| `BRANDED_COMMUNITY` | 정책의 기준값이 **모두 정해져 있고** 모두 충족 | Forever Rank 커뮤니티 레벨 랭킹 |
| `OFFICIAL` | 활성 캐릭터가 모두 공식 공급원 데이터 | 공식 데이터 기반 레벨 랭킹 |

- 기준값이 하나라도 `null`(미정)이면 2단계로 올라가지 않습니다.
- 제출자 수를 모르면(`null`) 2단계로 올라가지 않습니다.

## 5. "전체 서버 1위" 표시 조건 (`evaluateServerWideClaim`)

아래를 **모두** 충족해야 합니다. 하나라도 막히면 "Forever Rank 확인 캐릭터 중 N위"로 표시합니다.

| 조건 | 막힘 코드 |
|---|---|
| mock이 아님 | `TEST_DATA` |
| 데이터가 있음 | `NO_DATA` |
| 활성 캐릭터가 모두 공식 공급원 (사용자 제출만으로는 불가) | `NOT_OFFICIAL_SOURCE` |
| 정책 기준값이 모두 정해짐 | `POLICY_UNDEFINED` |
| 모집단 수를 공식 근거로 앎 | `POPULATION_UNKNOWN` |
| 확인 캐릭터 ÷ 모집단 ≥ 기준 | `LOW_POPULATION_COVERAGE` |
| 검증 비율 ≥ 기준 | `LOW_VERIFIED_RATIO` |
| 식별 충돌 비율 ≤ 기준 | `IDENTITY_CONFLICTS` |

데이터 최신성은 7일 기준(`staleAfterDays`)으로 이미 걸러진 활성 캐릭터만 세는 방식으로 반영합니다.

현재 결과: **어떤 데이터로도 허용되지 않습니다.** 공식 공급원이 없고, 모집단을 모르고, 기준값이 미정이기 때문입니다.

### 기준값을 정하는 절차

1. 공식 API로 모집단(전체 캐릭터 수 또는 전체 목록)을 얻을 수 있는지 확인합니다.
2. 실제 데이터에서 커버리지·검증 비율·충돌 비율 분포를 기록합니다.
3. 명세서를 먼저 고치고 `config/community-ranking.ts`에 값을 넣은 뒤, `status`를 `APPROVED`로 바꿉니다.

## 6. 화면 표시

랭킹 화면 상단 "데이터 안내" (`components/ranking/data-scope-panel.tsx`):

```text
[커뮤니티 랭킹] 순위는 Forever Rank가 확인한 캐릭터 안에서의 순위입니다.
데이터 기준  2026년 10월 7일
데이터 범위  Forever Rank가 확인한 캐릭터 128명 (최근 7일)
데이터 출처  커뮤니티 제출
검증 상태    커뮤니티 제출
```

- "전체 서버" 문구는 locale에 `rankings.rankScope.serverWide` 한 곳에만 있습니다.
- 그 문구는 `evaluateServerWideClaim`이 허용할 때만 씁니다. 테스트가 이 규칙을 확인합니다.
